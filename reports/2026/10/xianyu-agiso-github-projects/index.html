源码说明了哪种接入原理

账号登录态／Cookie→网页 HTTP／WebSocket→规则或大模型→消息回复／发密

XianYuApis 的 goofish_live.py 实现 WebSocket 消息发送；XianyuAutoAgent 的 main.py 取商品信息和会话上下文，调用 generate_reply 后发送。TypeScript SDK 的 orders.ts 包装订单详情与虚拟发货 MTOP 方法。这些代码体现的是网页登录态和网页协议接入，不能当成开发者拥有官方开放平台权限的证明。

xianyu-auto-reply 的 auto_delivery_handler.py 会匹配规则，并区分固定文字、数据卡券、图片、API 货源等内容；数据卡券调用 consume_batch_data 取码，再进入发送和记录流程。这里确认的是实现存在，未审计其支付确认、所有库存一致性或当前平台兼容性。

发送卡密消息、把订单标为已发货、买家成功兑换，是三种不同结果。读到相关接口和代码，不等于实测完成整条交易。

阿奇索：找到接口研究资料，未找到核心实现

agiso-open-platform-workspace 是本次最直接的线索。它把阿奇索公开资料整理为文档、索引和 Skill，并有签名辅助脚本。闲鱼分区 aldsIdle 中列出订单查询、执行自动发货、发消息、付款通知等内容；这是第三方保存的资料快照，当前权限和准确性仍应回到阿奇索确认。

值得继续核实的入口：/ImMsg/SendMsg（订单相关消息）、/Assistant/SendImMsg（回复助手原始消息）、IdleTradePay（付款通知）、IdleReceiveClientMsg（助手收到消息）。快照的接收类型列出图片、付款、创建订单卡片，没有据此证实任意普通文本消息可完整推送。不能把“能发送文字”直接推导成“能接所有文本咨询”。

LimboMusic/xianyu_master 则通过页面定位器操作阿奇索相关后台，并不是阿奇索服务端源码。另一个 zymzzz/agiso 的当前仓库仅有 README、LICENSE 和 gitignore，缺少可用 SDK 实现，未列为推荐候选。

本次没有找到可核实的阿奇索核心服务端开源实现；也没有把其他闲鱼项目的协议实现冒充阿奇索自身方案。

按目标选阅读入口

  1. 理解“怎么连自己的账号”：先读 XianYuApis 的登录和 goofish_live.py，再读 XianyuAutoAgent 的消息处理。
  2. 理解“付款后怎么从库存发码”：读 xianyu-auto-reply 的 auto_delivery_handler.py 和 card_service.py。
  3. 准备 Node.js 自研：研究 xianyu-sdk-ts 的 client、live、api/orders 模块。它有源码与测试文件，当前账户可用性尚未核验。
  4. 保留阿奇索连接层、自己写业务：先利用 agiso-open-platform-workspace 定位资料，再向阿奇索核实所需权限、现行接口与消息范围。

这是一份研究入口建议，没有安装依赖或选定生产实现。尚无账户侧结果支持“直接部署即可稳定使用”的结论。

使用前最相关的事实边界

条款：xianyu-auto-reply 的 LICENSE 是 AGPL-3.0，而 README 又增加禁止商业用途说明，口径不一致，商用复用前应找作者澄清。XianYuApis 只有 README 的 MIT 标记；xianyu-sdk-ts 在 package.json 声明 MIT，均未在本次树快照见独立 LICENSE 文件。

近期反馈：XianyuAutoAgent 在 2026-09-29 有“登录成功但读不到消息”的未关闭 Issue；xianyu-auto-reply 在 2026-10-14 有与闲鱼助手循环对话的用户报告。这些是具体用户个案，没有在本次复现，不能推出所有账户都会失败，也不能由星数推导稳定性。

维护与成本：只记录可验证的仓库时间和内容；未测部署成本、吞吐、维护工时或账号风控概率。没有执行远程安装脚本、安装第三方 Skill 或调用任何发消息／发货接口。
