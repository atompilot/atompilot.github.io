SessionPlane · Client decision

PWA 先行，
原生能力后接。

React Native 可以做，但它不该成为第一版的前置条件。先用网页把“看见同一会话、明确目标后输入”做可靠，再把通知、Face ID 和系统入口放进原生壳。

Recommended Web-first
Native-ready

移动端长期可以有 App；第一版仍以响应式 Web/PWA 为主。协议和认证从第一天保持客户端无关。

一句话判断

原生 App 的优势集中在“系统集成”，而 SessionPlane 最难、最核心的部分是“终端正确性”。终端生态本来就在浏览器侧，因此先做 PWA 能更快验证核心，又不会堵死 React Native。

三种路线，
不是二选一。

这里比较的是第一版应该承担什么，而不是哪项技术“更高级”。背景连接在 iOS 上无论网页还是原生都不能被当作永久在线链路；可靠通知应由服务端推送，前台再重连实时会话。

Target architecture

核心协议先独立，客户端才有选择。

Host、session stable ID、pane generation、只读输出和显式输入命令都属于协议层。它们不应该知道前端来自 Safari、Home Screen PWA，还是 React Native App。

Client 01 · NowResponsive Web / PWA

session 列表、终端观察、命名、受控输入、断线与过期目标提示。

Shared coreProtocol + auth + terminal web module

TypeScript 数据合同、WebSocket 事件、目标世代校验；终端用 xterm.js。

Client 02 · LaterExpo / React Native shell

原生导航、通知、SecureStore、Face ID；终端区域通过 WebView 复用 Web terminal module。

Remote coreControl service + Mac Host Agent

Mac 主动出站连接；公网不直接暴露 tmux socket 或 Host Agent。

实施顺序。

第一版的目标是形成可信的远程接管闭环，不是一次性把所有原生能力备齐。每一步都由真实设备证据决定下一步。

把 Web 版做成可长期使用的客户端

将轮询快照替换为 PTY/WebSocket，接入 xterm.js，完成认证、断线重连、离线不补发与 stale target 拒绝。

在 iPhone/iPad 真机上连续使用

验证软键盘、横竖屏、长输出、弱网恢复、Home Screen 启动和 Web Push；记录具体摩擦，而不是预设 App 必须存在。

命中原生触发条件后做 Expo 壳

复用协议包与终端 Web 模块，原生实现 SecureStore、Face ID、通知动作和深链，不复制 Host Agent 或会话状态。

何时值得做 App

出现下面任一项被真机证据反复确认时，原生客户端就从“可选”转为“该做”。

  • Web Push 或通知动作不足以处理待输入事件
  • 需要 Face ID 才允许进入输入模式
  • Safari/PWA 的软键盘持续破坏终端操作
  • 需要小组件、快捷指令或系统级快速入口
